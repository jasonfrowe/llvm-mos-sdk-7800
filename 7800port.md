# Atari 7800 LLVM-MOS Port Status

Last updated: 2026-09-12

## Purpose

This document summarizes the work completed to implement Atari 7800 support in this LLVM-MOS SDK fork, along with current limitations and next priorities.

## Emulator Used

Primary emulator workflow used during bring-up:
- a7800 emulator (local user install)

Additional tooling used with emulator validation:
- 7800basic 7800sign for hash/signature compatibility checks on A78 outputs

Notes:
- Emulator paths are intentionally not hardcoded in project files.
- Current workflow is manual build, sign, and run.

## Target and Build Output

- Target name: atari7800
- Compiler driver: mos-atari7800-clang
- Cartridge output: A78 format
- Current ROM model: 32 KiB baseline

### How to build

One-time setup (already done in this repo, `build/dev-bootstrap` exists). Auto-downloads the LLVM-MOS bootstrap compiler on first configure:

```sh
cmake -S . -B build/dev-bootstrap -G Ninja
```

Build everything for a platform (the right way -- runs the install step, so the output you look at is actually fresh):

```sh
cd build/dev-bootstrap
ninja atari7800-examples            # flat platform: palette-demo, astrowing, pokey-min, title-demo, etc.
ninja atari7800-supergame-examples  # SuperGame platform: bank-min
```

Outputs land at:
```
build/dev-bootstrap/examples/atari7800/astrowing.a78
build/dev-bootstrap/examples/atari7800-supergame/bank-min.a78
```

**Gotcha**: each platform's examples actually build in a *nested* CMake project at `build/dev-bootstrap/examples/<platform>/build/`. Running `ninja astrowing.a78` from inside that nested directory recompiles the object but skips the install step, so the outer `.a78` you'd normally check stays stale (this bit us in priority #21 below). Always invoke the top-level `ninja <platform>-examples` target from `build/dev-bootstrap`, never `cd` into the nested build dir.

## Memory Layout (Current)

Hardware windows:
- RAM: 0x1800-0x27FF
- ROM: 0x8000-0xFFFF

Linker/script strategy:
- A78 header: first 128 bytes of output file
- Reset trampoline placed at high ROM (0xF000) to keep signing/hash flows compatible
- Footer and vectors reserved at top of ROM for 7800 signing compatibility

Runtime scene buffer placement:
- Scene zones are split into two banks to avoid physical shadow/conflict regions:
  - Low scene zones in .scene_zones_low at 0x1A00
  - High scene zones in .scene_zones_high at 0x2200
- Current scene zone size: 64 bytes per zone
- Default 8-line zone mode: 28 visible zones

Known sensitive regions (documented during bring-up):
- Physical shadow areas around low RAM stack/zero-page mirrors can corrupt display lists if buffers are placed incorrectly.
- Current split-zone mapping was introduced to avoid those collisions.

## Current Progress Snapshot

Current state is beyond initial bring-up and into gameplay-port readiness:
- Sprite rendering is stable in asset bridge demo
- HUD text can render with mapped Astro Wing glyph set
- Major linker/signing compatibility issues are resolved
- Scene memory collision issues have working mitigation

Porting status relative to Astro Wing:
- Asset ingestion path is working
- Runtime API is usable for sprite and basic HUD composition
- Work remains to make HUD/text updates cheap and deterministic every frame

## Current Issues

1. Vsync budget and frame-time pressure under heavier HUD updates
- Some text update patterns can cause visible instability (flicker, rolling artifacts, black frames).
- Current implementation needs stricter per-frame budgeting and lighter text submission paths.

2. Scene zone capacity limits
- Zone object lists are bounded by per-zone bytes.
- Over-submission in the same zone can overflow practical limits and destabilize output.

3. RAM headroom is still tight
- 6502 timing and memory margins are narrow; runtime code paths must stay minimal.
- Additional gameplay systems have not yet been layered on top of full HUD + scene load.

4. Text path maturity
- High-level scene_draw_text is functional but still needs hard guards and predictable behavior under all HUD loads.
- A pre-indexed glyph-run path (7800basic-style) is still preferred for hot frame loops.

5. Tooling integration gaps
- Build-integrated signing and emulator launch are not yet fully automated in-repo.

5. ~~Adopt persistent sprite objects (7800basic-style)~~ (Done 2026-09-05)
- 7800basic's runtime (`~/Software/Atari7800/7800basic/includes/updateobjects.asm`, `zonememory.asm`) doesn't re-derive zone membership and re-append a fresh object header every frame the way our `atari7800_scene_draw_sprite` + `begin_frame`/`end_frame` did. It assigns each sprite a persistent slot and patches its existing header in place frame-to-frame. Also confirmed 7800basic's default zone height is 16, not 8 (matching the half-built `ATARI7800_ZONE_HEIGHT=16` option already in this codebase, not yet adopted). Checked cc65's Atari 7800 target too -- it's conio/text-console only, nothing relevant to sprites.
- Added `atari7800_scene_object_t` / `atari7800_scene_sprite` / `atari7800_scene_hide_sprite` to `mos-platform/atari7800/atari7800.{h,c}`, adapted from 7800basic's model with one correction: slots are local to whichever zone an object currently occupies (not global across every zone) since our display lists are compact-plus-terminator, unlike 7800basic's always-fully-populated zones -- a global slot would leave stale bytes in the gap between non-adjacent occupants sharing a zone. Moving to a new zone parks the old slot off-screen rather than reclaiming it, so a zone's slot usage only grows even if live occupancy shrinks -- a known, narrow limitation for scenes with heavy zone-crossing churn, not hit by anything in `astrowing.c` today.
- `astrowing.c` migrated all 4 stars and both ship-half sprites to persistent objects and dropped its per-frame `begin_frame`/`end_frame` calls entirely. HUD text is untouched (already handled by static zone residency, priority #3).
- Re-measured with the same frame-budget marker: total overrun dropped from 38 scanlines to roughly 15 (~6% of the visible screen, down from ~27% where this investigation started). Visually confirmed correct in the emulator (ship, stars including hide/show at the y=16 HUD boundary, HUD text).
- Resolved the hue-labeling confusion from the initial measurement: disassembly plus a targeted A/B test (rebuilding with the game-logic marker write removed) confirmed game logic contributes zero visible overrun (fully absorbed in vblank) and the **entire remaining ~15-scanline band is the star + ship persistent-object draw calls themselves** (6 sprite plots/frame). The earlier "0x8f = green" color attribution from the very first round of measurement was simply wrong and never independently re-verified; it's actually light blue. Not chased further tonight -- 15 scanlines (~6% of the visible screen) for 6 sprite draws is a reasonable baseline to build more gameplay on and re-measure once there's more on screen, rather than over-optimizing this toy scene now. The `ATARI7800_ZONE_HEIGHT=16` option remains an available lever if a future scene needs more headroom.

7. ~~NMI-driven display sync~~ (Done 2026-09-05, doesn't help this scene)
- Adapted 7800basic's MARIA-fired-NMI kernel synchronization (`~/Software/Atari7800/7800basic/includes/std_routines.asm`'s `visibleover` toggle) into `atari7800_scene_enable_nmi_sync` / `atari7800_scene_wait_active_start` / `atari7800_scene_wait_display_safe` in `mos-platform/atari7800/atari7800.{h,c}`. First-ever use of the platform's NMI vector; verified correct via disassembly (proper register save/restore, ends in `RTI`) and confirmed no regression in `palette-demo`/`displaylist-demo`/`asset-bridge-demo` (none of which opt in, so NMI never fires for them).
- Hit and fixed a real design bug along the way: the first version's `wait_display_safe()` didn't actually let logic overlap active-display time (a single level-triggered wait called after logic just idles away the safe window before ever reaching busy time). Needed splitting into `wait_active_start()` (before logic) / `wait_display_safe()` (before draws) to get real overlap, matching how 7800basic's `drawscreen` waits bracket the *whole* loop body from the outside, not something sandwiched in the middle.
- **Result: doesn't help `astrowing.c`.** Game logic was already measured as effectively free (sub-scanline, absorbed in blanking) hours earlier -- the entire benefit of this mechanism is letting logic overlap active-display DMA time, and there's no benefit to overlapping work that was never expensive. The actual bottleneck is draw-call cost itself, which no amount of loop restructuring can reduce. Kept in the SDK as validated infrastructure for a future logic-heavier scene; `astrowing.c` stays on it since it's correct and no worse than the old polling model, just not the fix this scene needed.

8. ~~Switch astrowing.c to 16-line zones~~ (Done 2026-09-05)
- astrowing.bas (the reference source) uses `set zoneheight 16`; confirmed 7800basic's own default is 16 too. Enabled via `#define ATARI7800_ZONE_HEIGHT 16` before including the platform header (already-scaffolded, previously never actually exercised by anything).
- **Found and fixed a real, previously-latent platform bug in the process**: `ATARI7800_ZONE_OFFSET` (the MARIA DLL "lines-1" encoding used both in the static blank-DLL builder and every dynamic zone-link call) was defined as `0u` for 16-line zones instead of `15u` -- MARIA was being told every zone was 1 scanline tall instead of 16, derailing the entire display list's timing and corrupting most of the visible screen. This has presumably been silently wrong since 16-line zones were first scaffolded; nothing ever exercised that code path before tonight. Fixed in `mos-platform/atari7800/atari7800.h`; the static blank-builder in `atari7800.c` now uses the named constant instead of a second hardcoded (and, for the 16-line branch, wrong) literal.
- Re-measured with the same frame-budget marker: overrun dropped from 66 to 52 scanlines (~29% reduction) on top of the NMI-synced loop. 52 scanlines is still a real overrun -- not chased further tonight.

**Correction (same night, caught by hands-on testing, not automated screenshots):** the first version of this also tried simplifying the ship from two manually-split 8-line objects to one `atari7800_scene_object_t` drawing `spaceship_frames[angle]` directly as a single 16-line object, reasoning that since it's natively 16 lines tall it should fit one 16-line zone exactly. **This was wrong and shipped broken** -- only the bottom half rendered. Confirmed by a controlled A/B test (same pinned rotation angle, single-object vs. two-stacked-objects, side by side in one screenshot): a single MARIA Direct Mode object empirically renders only ~8 scanlines *regardless of the containing zone's declared height*. 16-line zones let a *zone* span 16 scanlines and let *multiple* objects share that zone, but an individual object still needs splitting to cover more than half of it -- matching 7800basic's own docs ("to use taller sprites, simply define more sprites and position one above the other") and its `EnableObject`/`SetObjectY` macros, which use a *different* bit (`%00010000` for zoneheight=16 vs `%00001000` for zoneheight=8) to select which half of a 16-line zone an 8-line object occupies -- i.e. 7800basic never draws a genuine single 16-line-tall object either.
- Reverted the ship to two stacked 8-line objects (`ship_top_obj`/`ship_bottom_obj`, at y=80/88) -- the only change from the original 8-line-zone code is that both objects now land in the *same* 16-line zone instead of two separate zones.
- The same root cause explained a second bug: stars scrolling in and out of view in 8-pixel bands. `draw_sprite_fine`'s fine-Y shift (`y & 7`) can only reach the bottom half of whatever 16-line zone a star is in, since it only has one reference point into `star_sprite_data`. Fixed by giving the star asset a second reference (`star_sprite_upper`, an 8-page-shifted view into an extended `star_sprite_data`) and selecting between the two at the call site based on `(y & 15) < 8` -- same half-select principle as the ship, generalized to a single-pixel sprite.
- Both fixes verified in the emulator (ship renders complete at a pinned rotation angle; stars stay visible across a longer, more-scrolled run).

9. ~~Fix persistent-object zone corruption~~ (Done 2026-09-06)
- **Process note first**: the user re-tested the "ship half-rendered / stars gap" fix above (commit `73559d9`) via `build/dev-bootstrap/examples/atari7800/astrowing.a78` and still saw the old bugs. Root cause was mine, not the code: that path is the OUTER, installed copy from a nested ExternalProject build (`build/dev-bootstrap/examples/atari7800/build/atari7800/astrowing.a78` is the real, freshly-compiled artifact); several verification rounds had rebuilt only the nested copy (`ninja astrowing.a78` from inside the nested build dir) without re-running the install step, so the outer file the user actually tested was stale. Fix: always rebuild via `ninja atari7800-examples` from `build/dev-bootstrap` (the full top-level target, which runs the install step), never the nested shortcut.
- With a properly fresh build in hand, the user hands-on-tested again (real keyboard input, not headless) and found two *further*, genuine bugs, both in the persistent-object model (`atari7800_scene_sprite`) added in priority #5:
  - **Stars vanish sharing a row with the ship/enemy.** `atari7800_maria_plot_sprite_zone5` always writes 7 bytes per object (5 header bytes + 2 "terminator" bytes that double as the *next* slot's first 2 header bytes). That's correct when a zone's whole object list is rebuilt fresh in one pass (the old `atari7800_scene_draw_sprite` model), but `atari7800_scene_sprite`'s "patch in place" path also went through that same 7-byte write on every per-frame redraw of an *already-placed* object -- silently zeroing the address/mode bytes of whatever occupies the next slot in that zone. Since the ship/enemy claim their zone slot once, early, and hold it indefinitely, they reliably end up at a *lower* slot number than any star that later drifts into their zone; since the game loop draws ship/enemy *after* stars, their redraw stomped the star's header every single frame.
  - **Stars vanish permanently after scrolling a bit, except near the top.** Persistent-object slots are parked (not reclaimed) on a zone change (see priority #5's own noted limitation) -- so a star re-entering a zone it had already visited before burns a brand-new slot every time, never reusing one. A 64-byte zone holds ~12 slots; four stars continuously crossing zone boundaries while scrolling exhaust a commonly-revisited zone's budget within a couple hundred frames, at which point `atari7800_scene_sprite` returns `ATARI7800_ERR_BUDGET_FULL` -- and because the object's `zone_index` bookkeeping isn't rolled back on failure (its *old* slot was already parked off-screen earlier in the same call), it stays permanently parked and keeps failing the same way forever. Zones visited less often (near the top of the scroll range) hadn't yet exhausted their budget, matching the reported "only visible near the top" symptom exactly.
  - Both are inherent to "patch in place forever" once more than one object can share a zone -- not fixable by tuning constants. Fixed by moving stars/ship/enemy in `astrowing.c` back to `atari7800_scene_draw_sprite` + `begin_frame`/`end_frame` (priority #4's model, still fully correct and already in the codebase): every zone's object list is re-derived from scratch each frame in that frame's own draw order, so there's no cross-frame slot staleness and no unbounded growth. The persistent-object API stays in the platform for genuinely static content (the HUD zone still uses it safely, since it never crosses a zone boundary) -- its doc comment in `atari7800.h` now spells out the zone-crossing-churn caveat explicitly.
  - Also fixed the underlying corruption at the platform level regardless: added `atari7800_maria_patch_sprite_zone5` / `atari7800_maria_patch_sprite_asset_zone5` (5-byte-only rewrite, doesn't touch the next slot) and switched `atari7800_scene_sprite`'s patch-in-place branch to use it. This doesn't fix the slot-growth issue (still real, still documented), but means a future caller of the persistent-object API for a *zone-stable* multi-object zone won't hit the header-clobbering bug astrowing.c did.
  - Verified with a temporary, reverted test-only change forcing continuous thrust (real keyboard testing wasn't available headless) to actually exercise scrolling: 6 snapshots from 3-20 seconds of continuous forced scrolling all show all stars still rendering as clean single-pixel dots at varying positions (never collapsing toward only the top), ship rendering complete, no corruption artifacts. The change was reverted before committing; `git diff --stat` after revert shows only the intended 3 files (`astrowing.c`, `atari7800.c`, `atari7800.h`).

10. ~~Fix enemy disappearing when a star shares its row~~ (Done 2026-09-06)
- Immediately after the fix above, the user hands-on-tested again and found a *third* bug (not yet present in their earlier reports): "if a star and the enemy sprite share the same row, then the enemy sprite disappears."
- Repro'd with a temporary, reverted test hack forcing a star to the enemy's exact (x, y): confirmed via pixel-level screenshot analysis that with the two objects at the exact same position, *neither* renders at all (not even the enemy's own multi-color sprite art, which briefly got misdiagnosed mid-investigation as a "corrupted overlap" before double-checking a clean baseline showed the same pink/green/yellow pattern is just the fighter sprite's actual art). Narrowed the trigger condition with further controlled tests: two Direct Mode objects needing pixel data on the *same 8-line scanline band* (confirmed via this session's own earlier finding that objects render in ~8-line units regardless of zone height) *and* overlapping in X both fail to render; separating them by X, or by scanline band (e.g. top vs. bottom half of a 16-line zone), renders both cleanly every time.
- This is a genuine MARIA Direct Mode hardware characteristic, not a software bug: Direct Mode has no per-pixel object-priority resolution, so two objects contending for the same physical scanlines and pixel columns produce undefined (here: both blanked) results. Not fixable underneath callers in the platform -- the fix has to be at the draw-order/game-logic level, avoiding the collision before it happens.
- Added a small `bands_collide()` helper to `astrowing.c` (approximate AABB check: same `y >> 3` 8-line band, plus a generous ±10px X window) and used it to skip drawing a star for one frame if it would land on the same band and overlap in X with the enemy or either ship half. Verified: forcing exact overlap with the guard active renders the enemy's normal complete sprite (star silently skipped that frame); disabling the guard with the same exact overlap reproduces total disappearance again, confirming the guard is both necessary and sufficient for this case. A 20-second stress run (continuous forced thrust, same technique as priority #9) shows the enemy rendering correctly in every sampled frame.
- Not generalized into the platform: this is scoped to astrowing.c's specific objects (stars vs. enemy/ship). Any future object added to this scene that can share a scanline band with another (bullets, asteroids) will need the same kind of avoidance check -- worth revisiting as a small reusable helper if/when several object types need mutual collision-band awareness, but not before there's a second real caller.

**Correction (2026-09-06, same investigation continued): priority #10's diagnosis was wrong.** The user pushed back after re-testing: the enemy still disappeared sharing a row with a star regardless of X distance, contradicting the "X-overlap" theory, and flagged that the whole display-list-building approach needed rethinking -- pointing at the 7800 Software Guide (7800.8bitdev.org) and the 7800basic compiler source/docs as references. The guide's own account of MARIA Direct Mode headers (4/5-byte layout, width-field formula, terminator convention) matched this SDK's implementation almost exactly, which didn't fit "hardware can't handle two objects on a line" either -- real 7800 games routinely have far more than two objects per scanline.

## 11. ~~Fix ATARI7800_ZONE_HEIGHT not actually reaching the compiled scene code~~ (Done 2026-09-06)

**The actual root cause, months in the making**: `mos-platform/atari7800/atari7800.c` is compiled exactly *once*, into a prebuilt static library (`libc.a`), as part of SDK bootstrap -- before any example (including `astrowing.c`) is ever compiled. That compile uses the header's *default* `ATARI7800_ZONE_HEIGHT` (8), because nothing at that point can know astrowing.c wants 16. `astrowing.c`'s `#define ATARI7800_ZONE_HEIGHT 16` only ever affected its own translation unit -- it had zero effect on any function inside `atari7800.c` (`atari7800_scene_draw_sprite`, `atari7800_scene_sprite`, `atari7800_maria_build_blank_ntsc`, the whole zone/DLL machinery), which had been silently running on 8-line-zone geometry (`ATARI7800_ZONE_SHIFT=3`, 28 zones, 33 DLL entries) this entire time, while `astrowing.c`'s own reasoning (its half-select logic, its now-deleted `bands_collide` guard, the whole "ship needs two stacked 8-line objects" premise from priority #8's correction) assumed 16-line geometry. Two halves of the same program disagreeing about where zone boundaries are -- confirmed directly by dumping the linked binary's symbols: `atari7800_scene_display_list` was 99 bytes (33 entries) and `atari7800_scene_zones_low` was 896 bytes, both exactly the 8-line configuration, in a ROM that `#define`s `ATARI7800_ZONE_HEIGHT 16`.

This retroactively explains nearly everything chased across priorities #5 through #10 tonight as symptoms of this one bug, not real MARIA hardware behavior:
- The "single Direct Mode object only renders ~8 scanlines regardless of the containing zone's declared height" finding (priority #8) -- there is no such cap; the library was always building 8-line zones.
- The ship needing two stacked 8-line objects, and the star needing two half-references -- unnecessary once zones are genuinely 16 lines.
- Priority #10's "MARIA Direct Mode has no per-pixel object priority, two objects on a scanline band corrupt" theory -- also wrong; the `bands_collide` guard happened to mask the real bug in some test configurations by accident, not because scanline-sharing is actually unsafe.

**The fix** (user chose this option explicitly over just hardcoding one zone height platform-wide): moved every zone-height-dependent piece of `atari7800.c` -- the zone/DLL static state and every function that touches `ATARI7800_ZONE_SHIFT`/`ATARI7800_SCENE_VISIBLE_ZONES`/the zone buffers (`atari7800_maria_build_blank_ntsc`, `atari7800_scene_init_160a`, `atari7800_scene_begin_frame`/`end_frame`, `atari7800_scene_set_zone_static`, `atari7800_scene_draw_sprite`, `atari7800_scene_sprite`/`hide_sprite`, `atari7800_scene_draw_text`/`draw_glyph_run`, the NMI machinery) -- into `static`/`static inline` definitions directly in `atari7800.h`, so they compile fresh into each program's own translation unit and genuinely honor that program's own `#define ATARI7800_ZONE_HEIGHT`. `atari7800.c` now contains only the handful of truly zone-height-independent functions (vblank/palette/low-level 5-byte-header plot/patch functions, glyph-run building), and defines `ATARI7800_NO_SCENE_IMPL` before including the header so it doesn't also pull in a second copy of the zone-height-dependent block (which would otherwise collide with every program's own copy, in particular the real, non-static `nmi` symbol the linker's weak-vector-override needs -- hit and fixed this exact duplicate-symbol error during the refactor). Documented the resulting constraint clearly in the header: use the scene API from exactly one `.c` file per program (already true of every example in this SDK).

## 12. ~~Fix garbage/duplicate pixels from assets sized for the old 8-line render window~~ (Done 2026-09-06)

Immediately after priority #11 landed, the user hands-on-tested and found three new artifacts: a solid yellow line above the enemy sprite, every star plotted twice (~8 lines apart), and stray dashes above the HUD text. All three turned out to be the same underlying cause, exposed (not created) by priority #11's fix -- assets that were sized/designed assuming a Direct Mode object's render window only ever covered ~8 lines (the old, broken behavior), now that objects genuinely render their *zone's* full declared height (16 lines) regardless of the object's own content:

- **`fighter_sprite_data`** (enemy) and **`hud_font_data`** (HUD glyphs), both in `examples/atari7800/assets/fighter.sprite.h`, were declared with an *implicit* array size (`uint8_t foo[] = { [1792] = ..., ... }`), which the compiler sizes to just past the highest explicit index -- covering only their real 8 pages (2048 bytes) of pixel data. A 16-line object now reads 16 pages regardless, so the extra 8 pages read whatever ROM bytes the linker happened to place immediately after each array (unrelated code or data) instead of blank. Given the "vertically flipped for MARIA scanline countdown" layout both assets already used (noted in their own comments), this garbage lands at the *top* of the object's zone rather than the bottom, matching exactly what was reported: a stray line above the enemy, stray dots above (not below or overlapping) the HUD text. Fixed by explicitly sizing both arrays to 4096 bytes (16 pages) so the extra 8 pages are explicit zero instead of adjacent ROM garbage -- harmless in an 8-line zone too (e.g. `asset-bridge-demo`, which doesn't override `ATARI7800_ZONE_HEIGHT`), since only the first 8 pages are ever read there.
- **`star_sprite_data`** (`astrowing.c`) hit a different failure mode from the same cause. Its two-reference design (`star_sprite` / `star_sprite_upper`, one pixel at page 7 and one at page 15) was built so that each reference's *effective* 8-line render window would isolate one pixel from the other -- back when the window really was 8 pages regardless of which reference was used. With windows genuinely spanning 16 pages now, *any* fine-Y shift's window (`[shift, shift+15]` for `shift` in 0-7) includes both page 7 and page 15 simultaneously, so both pixels render at once, 8 lines apart -- doubling every star. Fixed by collapsing to a single reference (pixel at page 15 only, matching the same page-`(N-1)` placement the old proven-correct 8-line formula used, generalized to `N=16`), extending the fine-Y shift range from `y&7` to `y&15` in `draw_sprite_fine`, and explicitly sizing the array to 31 pages (7936 bytes) so the full `shift` range (0-15) never reads past explicit padding.
- Verified via pixel-level screenshot analysis (not just eyeballing): the yellow line above the enemy, the stray HUD dashes, and the duplicate star positions are all gone; a repeat of the 20-second continuous-forced-scroll stress test shows clean single-instance stars, a clean enemy, and a clean HUD throughout. All four demos re-confirmed visually correct, including `asset-bridge-demo` (which shares the now-repadded `fighter_sprite_data`/`hud_font_data` at the *default* 8-line zone height).

**Takeaway for future assets**: any sprite or font asset drawn into a 16-line zone needs to actually declare 16 pages of data (explicit trailing/padding zero bytes), even if the real art is shorter -- an object's render window is dictated by the *zone's* declared height, not the asset's own `height_lines` field (which nothing in this code path even reads). This wasn't visible before priority #11 because the platform was secretly always using 8-line zones; it's a real, permanent constraint now that zones are genuinely 16 lines.

## 17. POKEY re-investigation #3: real init sequence from 7800basic's own source; crash proven unrelated to any program content (Done 2026-09-07)

User asked to look at 7800basic's own POKEY-handling source directly (rather than continuing to guess at the emulator side), and separately flagged that the VGM/music player was ported from `PlayMusic`'s hand-written asm to C -- worth re-checking against the original too.

This platform's `atari7800_pokey_init()` only ever wrote `IRQEN=0` -- never `SKCTL`. Confirmed in MAME's own `pokey.cpp` that this is not cosmetic: `pokey_device::step_one_clock()` only advances the chip's internal clock/counters `if (m_SKCTL & SK_RESET)`, and `m_SKCTL` resets to 0 (in reset) at device construction -- meaning POKEY's counters would never have run at all under the old init, regardless of IRQEN, so audio could never have worked even if the crash weren't happening.
  - Rewrote `atari7800_pokey_init()` in `atari7800_pokey.h` to match the reference exactly: clear registers 0-15, set `XCTRL1`'s bits, `SKCTL=3`, `AUDCTL=0`.
  - **Rebuilt and re-tested against `pokey-min.a78` -- the crash was unchanged, identical address.** This new, hardware-accurate init sequence does not fix it.
- **Escalated the isolation further**: replaced `pokey-min.c`'s content with the most minimal possible program -- `int main(void) { for(;;) {} }`, no `#include`s of any kind, nothing POKEY-related whatsoever. **This still crashes, identically**, purely because the `.a78` header declares the POKEY@450 cart type. - **Traced where in the boot sequence the crash actually happens**, since the previous "PC in RAM" signal (priority #16) turned out to be a red herring: the real 7800 BIOS legitimately runs a chunk of its own boot code from console RAM before handing control to the cart (confirmed by reading `$FFFA-$FFFF` live during boot: it shows the *BIOS's own* vectors, e.g. `NMI=$F000, RESET=$F884, IRQ=$F933`, for the first ~35 frames, then correctly switches to reading this platform's real vectors, e.g. `NMI=$4021`, matching the linked ROM's own reset/nmi/irq addresses exactly). The crash happens in the narrow window during or immediately after that BIOS-to-cart handoff -- by the time the vectors read correctly as this program's own, the CPU has already landed in RAM executing garbage. This rules out anything in `main()` (there isn't any real code left to blame) and points at either the BIOS's own hardware-detection behavior when it sees a POKEY-declared cart, or a bug in this MAME fork's `a78_p450_t0` cart-slot device's handling of the handoff itself.

However, this was checked against the *32K* POKEY test from priority #16 too (vectors there point within the ordinary `$8000+` window, not the extra 48K-only bank) and it crashed identically, which argues against a low-bank-specific read bug and leaves this difference unexplained rather than confirmed.

Found and fixed one real behavioral bug: on the `0xFE` (end-of-song) marker, the original's `.EndSong` handler resets the pointer and `rts`s immediately -- the restarted song's first frame isn't read until the *next* call. This function instead fell through and kept processing the restarted song in the *same* call, silently playing an extra frame's worth of register writes every time a song looped. Also added the reference's `cpy #64` defensive cap (bail out after 64 bytes rather than looping indefinitely on malformed data) for full parity, though this was never observed to matter in practice. ## 18. POKEY re-investigation #4: memory-map audit against the official Software Guide; RIOT-RAM theory tested and refuted (Done 2026-09-07)

User provided the 7800 Software Guide's Appendix 1 memory map table directly and asked to audit this platform's own memory layout against it for sanity, given `$450` needs `$0400-$047F` ("available for external device mapping" per the guide) while `$0480-$04FF` is explicitly "6532 RAM. Don't Use."

- **Full audit of every region this platform's `link.ld` declares** (`zp` @ `$00A0-$00FF`, `ram_low` @ `$1800-$203F`, `ram` @ `$2200-$27FF`, `cart_rom` @ `$4000/$8000-$FFFF`) against every row of the guide's table: **zero overlap with any shadowed, RIOT, or reserved zone** -- `zp` sits inside "RAM Block Zero," `ram_low`/`ram` match the guide's own "RAM" rows byte-for-byte, and `cart_rom` sits entirely within "available for external device mapping" plus this platform's own signature/vector bytes in the reserved footer, exactly where they belong. This platform's memory map is confirmed sane and spec-compliant; it is not the source of the crash.
- **Formed a promising-looking hypothesis and then disproved it**: since MAME's `a78_p450_t0` cart-slot device installs its `$0400-$04FF` handler (which returns `0xFF` for reads outside `$0450-$045F`) at `machine_start()` -- once, before the real BIOS ever executes a single instruction -- the guide's explicit "Don't Use" warning on `$0480-$04FF` raised the question of whether the BIOS's *own* boot sequence relies on that RIOT RAM for something, and would break under any POKEY-@450 cart regardless of what the cart itself contains. A quick heuristic byte-pattern scan of the real BIOS ROM (`~/.a7800/bios/a7800.zip`'s `c300558-001a.u7`) for absolute-addressing opcodes followed by a `$04xx` high byte produced a few apparent hits (`CMP $0490`, `CMP $04F0`) -- but this scan didn't respect real instruction boundaries and was reading garbage: a proper disassembly at the same file offset (using `capstone`'s MOS65XX support, installed for this purpose) showed the actual instructions there are `LDY $CD,X` / `CMP $CD,X` (zero-page,X mode) -- an unrelated coincidence of bytes, not a real reference. **A full, properly-decoded linear disassembly of the entire 16KB BIOS found zero instructions referencing any address in `$0400-$04FF`.** This refutes the RIOT-RAM-reliance theory; it is not supported by the evidence (with the standard caveat that a purely linear disassembly of a ROM containing embedded data can misalign after a data region, so this isn't a mathematical proof of absence -- but no evidence for the theory was found where the strongest candidate sites were checked directly).
- **Where this leaves the investigation**: three independent, targeted hypotheses have now been tested and eliminated -- the `.a78` header/cart-type bits (found and fixed a real but unrelated v4-byte-order bug, priority #16), the POKEY init sequence (rewritten to exactly match 7800basic's own `detectpokeylocation`, priority #17), and this platform's own memory map (confirmed clean against the official spec) and the BIOS's reliance on the disputed RAM region (checked directly, not found). The crash reproduces in a program containing no code at all (priority #17's `pokey-min.a78`), purely from the cart-type declaration, during the BIOS-to-cart handoff. At this point the remaining plausible explanations are a genuine bug specific to this MAME fork's `a78_p450_t0` device implementation (not something fixable from this SDK's side), or a real, physical-hardware POKEY-cart quirk this emulator is faithfully reproducing that 7800basic's own toolchain/runtime happens to avoid for reasons not yet identified. Further progress from here would benefit from either real hardware, a MAME build with actual breakpoint/step debugging (this Lua binding still doesn't expose write-watchpoints), or checking with the wider 7800 homebrew community (7800.8bitdev.org/AtariAge) for whether this specific a7800 MAME fork's POKEY-@450 support has a known issue.

- **With both of those fixed, a real watchpoint on `$0400-$04FF` and `$00F0-$00FF` finally worked**, and immediately explained everything: a burst of writes to zero-page `$00FE` with steadily *incrementing* values (`0x24, 0x25, 0x26, 0x27...`), from a tight 3-byte-stepping loop -- but at **PC `0x04E9`**, i.e. *inside the very `$0400-$04FF` range the POKEY cart-slot device was hijacking*. The mechanism: this fork's `a78_p450_t0` device installed its handler over the *entire* `0x0400-0x04FF`, but the 7800 Software Guide's own memory map (Appendix 1, supplied directly by the user this session) says only `0x0400-0x047F` is "available for mapping by external devices" -- `0x0480-0x04FF` is real, general-purpose 6532 RIOT RAM, already backed by genuine storage in the base `a7800_mem` address map, and explicitly documented as "Don't Use" for exactly this reason. - **Build flags, confirmed directly from the actual config files rather than assumed**: `MinSizeRel` (`-Os`-equivalent) is this project's own CMake default (`CMakeLists.txt`), and every example's `target_compile_options` also explicitly passes `-Os`. `-flto` is baked into `mos-common.cfg` (`@`-included by every mos target's own platform `.cfg`, confirmed by reading it directly), so it's active for every build in this SDK without needing to be repeated per-target. Not a debug build, not missing LTO.
- **Audited `astrowing.c` and the platform header against the guide's specific rules**: no function pointers (so `-fnonreentrant`/`__attribute__((leaf))` don't apply here), no non-static function-local `const` arrays, no wide (32/64-bit) integer types anywhere in the actual code. Two real findings, both fixed:
  - **None of `astrowing.c`'s own helper functions (`update_bullets`, `fire_bullet`, `update_enemy`, `draw_sprite_fine`, etc.) were declared `static`** -- meaning they carried external linkage into a single-file program with nothing else that could call them, which can keep the linker from treating them as safely inlinable/eliminable even under LTO. Marked all of them `static`; confirmed with a before/after link-map comparison (tracking `.cart_rom_reset_entry`'s address, which marks the end of linked content) that this alone recovered 256 bytes -- small, but real and free.
  - **`star_t stars[4]` was an array-of-structs**, which the guide explicitly calls out (SoA over AoS: indexing a 1-byte array is a plain offset, indexing an array of 3-byte structs needs a multiply first). Converted to `star_x[4]`/`star_y[4]`. Also found, while touching this code, that the struct's third field (`color`) was write-only -- set in `init_stars` but never actually read anywhere (the star sprite always draws in palette 4 regardless; `cycle_stars` animates that palette globally, not per-star) -- dropped it entirely rather than porting dead state. Recovered 2 more bytes; combined with the `static` fix, 258 bytes total.
  - **Assessment of that number against the actual budget problem**: 258 bytes is genuine, but small next to the ~7.4KB the two still-unconverted music tracks (`Song_03`, `Boss`) need on their own, let alone the ~1,900 remaining lines of collision/boss/blue-fighter/asteroid logic priority #22 already sized up. Code-quality hygiene like this is a good habit worth keeping (and revisiting again once more of the C source exists), but it isn't a substitute for deciding the bankswitching-vs-squeeze question raised in priority #22 -- that's still open.
- **"Are we missing vsync?" -- checked directly rather than inferred from the emulator's own "Average speed" percentage** (which reflects whether the *host* can keep the *emulated 6502 clock* running at real NTSC speed, not whether *this program's own loop* is keeping up with real vblank -- a genuinely different thing an overrun could silently violate without moving that number). Sampled `frame_count`'s live memory value (found via `llvm-nm` on the built `.elf`, same technique as priority #21's bullet trace) at two points exactly 120 real emulator frames apart during gameplay: it advanced by exactly 120. The game loop is keeping up with real vsync 1:1 right now, confirmed with a real measurement, not assumed. Flagged as something to keep re-checking incrementally as the much larger remaining systems (collision across many object types especially) get added, using this same technique -- there's no reason to expect it'll still hold once several hundred more lines of per-frame logic exist, only that it holds today.

## 24. SuperGame bankswitching: new `atari7800-supergame` platform, proven with a minimal cross-bank smoke test (Done 2026-09-07)

User decision, given the ROM-budget wall from priority #22/#23: SuperGame (Atari 7800 "Type 2" cart, 8x16KiB banks = 128KiB) becomes the default target for `astrowing` and future examples, planned and started now rather than squeezed around later. Existing small demos (`palette-demo`, `displaylist-demo`, `asset-bridge-demo`, `pokey-min`, `title-demo`) stay on the flat 32K/48K layout unchanged -- they don't need the room.

- **Hardware model** (confirmed against this SDK's own test emulator, `third_party/a7800/src/devices/bus/a7800/rom.cpp`'s `a78_rom_sg_device::read_40xx`/`write_40xx`, and the CPU-side install in `third_party/a7800/src/mame/drivers/a7800.cpp`): `$4000-$7FFF` fixed to bank 6 (second-to-last), `$8000-$BFFF` switchable among all 8 banks via a single byte write to *any* address in that range, `$C000-$FFFF` fixed to bank 7 (last, where vectors/reset must live -- the only bank guaranteed present at reset). Both fixed halves are mapped simultaneously at all times, so code in one calls code in the other directly with zero wrapper overhead; only a call crossing into/out of the switchable window needs a wrapper. Header bits for SuperGame+POKEY@450 (device `a78_rom_p450_sg_device`, MAME short name `a78_p450_t2`): v3 byte 53=0x00, byte 54=0x02 (Type 2 select) | 0x40 (POKEY@450, same bit already used for the flat header) = 0x42; ROM size field = 0x00020000 (128K). This device only overrides `read_04xx`/`write_04xx` on top of the plain SuperGame device, so the POKEY `$0400-$047F` fix from priority #19 already covers it -- confirmed via MAME's own verbose cart-detection log (`Starting Atari 7800 ROM Carts w/SuperGame Bankswitch + POKEY @ 0x0450 ':cartslot:a78_p450_t2'`), no emulator changes needed this time.
- **Had to become a separate platform, not a linker-script toggle within `atari7800`** -- the original plan was a per-program `-Wl,-T,link-supergame.ld` override, mirrored on `mos-platform/nes-mmc3`'s pattern. That failed immediately and unambiguously (`ld.lld: error: ... region 'zp' already defined`): this SDK's mos-clang driver always applies the current platform's own `link.ld` regardless of an additional explicit `-T`, so the two scripts merged and collided rather than one replacing the other. The real, working precedent (confirmed by rereading how `nes-mmc3`/`nes-nrom`/etc. actually work) is that every NES mapper variant is its *own platform* with its own `link.ld`, sharing the base NES code via `PARENT`. Mirrored that exactly: new `mos-platform/atari7800-supergame/` (`platform(atari7800-supergame COMPLETE PARENT atari7800)`), added to `mos-platform/CMakeLists.txt`'s and `examples/CMakeLists.txt`'s subdirectory lists. A program opts in simply by being built against `--target=atari7800-supergame` instead of `--target=atari7800`; the flat platform's own files were touched and then fully reverted, confirmed inert (`ninja atari7800-examples` showed every existing example "up-to-date", no rebuild triggered).
- **New `mos-platform/atari7800-supergame/link.ld`**: modeled on `nes-mmc3`'s `_prg-rom-banked.ld` LMA-aliasing trick (each switchable bank gets its own linker-global address, `bank_N * 0x10000 + 0x8000`, so all six alias down to the same real `$8000` CPU address once the low 16 bits are taken -- confirmed empirically further down, not just assumed), simplified since SuperGame's switch is one byte write with no MMC3-style register-select step. Two real bugs found and fixed while bringing the very first program up on it, both were genuine linker-script mistakes, not emulator issues:
  - `.cart_footer` (needs to sit at the fixed address `0xff80`) was placed into a `cart_rom_fixed_hi` region whose `LENGTH` I'd bounded to stop *at* `0xff80`, one byte short of actually containing it (`overflowed by 128 bytes`). Fixed by giving the region its full real 16KiB span and adding a second, narrower overlapping region (`cart_rom_fixed_hi_code`, mirroring the flat `link.ld`'s existing `cart_rom`/`cart_rom_code` overlap technique) for the reset trampoline, so a future overflow into the footer fails to link instead of silently colliding with it.
  - `mapper.s`'s `.zeropage __prg_8000` came back `undefined symbol` at link time. Traced this by objdumping the object file: `.zeropage`-declared symbols are emitted as specially-flagged *undefined* symbols, and -- unlike the `__rcN` imaginary registers, which `imag-regs.ld` explicitly assigns real addresses via arithmetic -- nothing in this SDK's shared linker scripts (nor, on inspection, in `nes-mmc3`'s own linker scripts, which use the identical `.zeropage` pattern and appear to have simply never been link-tested by any existing NES example) actually assigns `.zeropage` symbols an address. Fixed locally by reserving the byte explicitly in a small `(NOLOAD)` section ahead of the generic `.zp.bss` catch-all, rather than depending on undocumented/unproven automatic behavior.
- **New `mos-platform/atari7800-supergame/mapper.h`/`mapper.s`**: `set_prg_8000`/`banked_call_8000` API, mirroring `nes-mmc3/mapper.h`'s naming and `banked_call_8000`'s save-switch-call-restore shape exactly, reusing the same shared `mos-platform/common/crt/call-indir.S` helper five other mappers already use. `set_prg_8000` itself is just `sta __prg_8000 / sta $8000 / rts` -- no MMC3-style two-step register-select/retry loop needed, since SuperGame's hardware protocol really is that simple.
- **New `examples/atari7800-supergame/bank-min/bank-min.c`**: the smoke test, mirroring `pokey-min`'s isolation role. Fixed-bank `main()` calls `banked_call_8000` into three switchable banks in a loop, each setting a different `ATARI7800_BACKGRND` value, paced by a plain software delay loop (deliberately not `atari7800_wait_vblank()` -- see next point).
- **Verification, and a real methodology dead-end worth recording**: reading `ATARI7800_BACKGRND` ($0020) back via the CPU memory space to check whether it changed *always* returned 0, on both the new bank-min and the already-working `palette-demo` -- this emulator's `atari_maria_device::read()` (`third_party/a7800/src/mame/video/maria.cpp`) only implements one real register (`case 0x08`, vblank status); every other MARIA register, including BACKGRND, is write-only and reads back a hardcoded 0. Not a bug in this work, just a dead end in how I tried to observe it. Separately, `atari7800_wait_vblank()`'s MSTAT poll also never returns under this specific headless harness (confirmed identical, pre-existing behavior on `palette-demo` too, unrelated to SuperGame) -- worth another look someday, but out of scope here, which is why `bank-min.c` deliberately avoids it. The mechanism was instead confirmed correct through direct, positive evidence: (1) MAME's own verbose cart-detection log confirms the intended device; (2) a Lua script writing bank IDs 0-5 directly to `$8000` and reading back `$8000-$8002` shows *exactly* each bank's real compiled bytes (banks 0/1/2 show `set_color_bankN`'s actual opcodes; banks 3-5, correctly unused, read zero) plus `$4000`/`$c000` showing the fixed banks' real content (`SEI`/`JMP` -- `_start`'s and the reset trampoline's real first bytes); (3) `llvm-objdump` on the built ELF confirms `main`/`banked_call_8000`/`set_prg_8000`/`__call_indir` all compiled to the exact expected save/switch/call/restore shape; (4) most directly, a real screenshot taken via MAME's Lua `video():snapshot()` at frame 20 during actual execution shows one solid color and a second screenshot at frame 200 shows a visibly different solid color -- the cartridge cycling through its own switchable banks, rendered on screen, not inferred.
- Restructuring `astrowing.c`'s real content across the fixed/switchable banks is explicitly out of scope for this pass -- deferred until this smoke test's approach has had a chance to be reviewed.
- Full regression pass across all examples (including `astrowing.a78`, both visually and via stable steady-state PC addresses) shows no regressions from either fix.

## 25. Migrate astrowing.c onto atari7800-supergame: title screen into bank 0, flat platform retired (Done 2026-09-12)

The actual motivation for #24: `astrowing.c` was at the flat 48K platform's practical ceiling with ~85% of `astrowing.bas` still unported. This pass moves the one genuinely one-shot piece of the program (the title screen -- rendered once at boot, never touched again) into switchable bank 0, establishing the pattern future levels/bosses will each follow, while gameplay's per-frame hot path stays in the fixed region unchanged. The flat `astrowing.a78` target is retired (user decision) -- it can't accept any of the upcoming gameplay content anyway, so the file and its assets moved rather than duplicated.

- **New location**: `examples/atari7800-supergame/astrowing/` (moved whole, including its local `assets/` subfolder, from `examples/atari7800/astrowing/`). Dropped the dead, already-unreferenced `assets/title_screen_conv.h` leftover from an earlier, superseded title-asset conversion approach while touching this directory. `title_screen.h`/`song_title.h` (shared with the still-flat `title-demo.c`) physically relocated to `examples/atari7800/assets/` -- the project's already-established shared-asset directory -- so both programs can reach them via plain relative includes despite now living under different platforms' example trees.
- **Shared-header conflict, resolved via a guarded macro, not duplication**: `title_screen_data0`/`title_screen_data1`/`title_screen_zones`/`title_screen_chunk_x_offsets` (in `title_screen.h`) and the song byte array (in `song_title.h`) are tagged `ATARI7800_TITLE_BANK`, a macro defined identically in both headers (`#if defined(__ATARI7800_SUPERGAME__) ... section(".cart_rom_bank_0.rodata") ... #else ... (nothing) ... #endif`), guarded on the platform-specific macro already set in `mos-platform/atari7800-supergame/clang.cfg`. `title-demo.c` (flat platform) gets the empty expansion and is untouched; `astrowing.c` gets the real section attribute. `title_screen_loop` itself (defined in `astrowing.c`, not shared) gets `__attribute__((noinline, section(".cart_rom_bank_0.text")))` directly -- `main()`'s call to it becomes `banked_call_8000(0, title_screen_loop)` (`mapper.h`).
- **A real "section type conflict" compiler error, found empirically**: originally tagged both the function and the data arrays with the bare `.cart_rom_bank_0` section name. Code and const data can't share one exact section name (different required ELF section flags) -- fixed by using `.cart_rom_bank_0.text` for the function and `.cart_rom_bank_0.rodata` for the data, both still caught by `link.ld`'s existing `*(.cart_rom_bank_0 .cart_rom_bank_0.*)` wildcard into the same output region.
- **Fixed-region overflow, a real capacity problem this exposed**: even with the title screen banked out, `astrowing.c`'s remaining `.text`+`.rodata` still didn't fit `cart_rom_fixed_lo`'s 16KiB -- overflowed by 12670 bytes. Root cause: the platform's `c_readonly` default only ever pointed at `cart_rom_fixed_lo`; `cart_rom_fixed_hi`'s ~16KiB (minus the tiny reset trampoline + 128-byte footer) was sitting completely unused. Added a new bounded region, `.cart_rom_fixed_hi_extra` (`mos-platform/atari7800-supergame/link.ld`), mirroring `.cart_rom_reset_entry`'s "stay inside `cart_rom_fixed_hi_code`, not the full `cart_rom_fixed_hi`" rationale so overflow into the footer still fails to link rather than colliding with it. Moved `astrowing.c`'s own `misc_sprite_data` (7936 bytes) and `spaceship.h`'s `spaceship_data` (~5952 bytes) there via the same section-attribute technique -- comfortably covers the gap, and this new region is now the natural home for future large fixed-region assets that don't fit in `cart_rom_fixed_lo` alongside the code.
- **A 1-byte `.zp` overflow, and a real lesson about how adaptive LTO's zp promotion is**: `banked_call_8000`'s `__prg_8000` reservation (mapper.s, already a known cost from #24) pushed total zp usage 1 byte past this platform's 96-byte `zp` region -- confirming the flat predecessor was already using that region at 100% capacity with zero slack. First tried trimming a named global to compensate (`cycle_state`, itself a legitimate simplification -- it's a pure function of `frame_count` and never needed its own persistent byte, so it stayed removed) but the overflow persisted *unchanged*: relinking showed `.zp.bss` shrank by exactly 1 byte while `.zp.noinit` grew by exactly 1, net zero -- LTO's zp promotion turned out to adaptively refill whatever became available with some other temporary, rather than just leaving it free. The real fix constrains the compiler's own budget instead of fighting its allocation choices: `target_link_options(astrowing.a78 PRIVATE "-mlto-zp=95")` (one less than the inherited `-mlto-zp=96`), forcing it to leave exactly the 1 byte our extra reservation needs. Note this flag only takes effect via `target_link_options`, not `target_compile_options` -- with `-flto`, real codegen (and this budget) is a link-time concern; compile-time-only placement produced a silent "argument unused" warning and no effect.
- **Verification, matching the plan's own primary signal**: `llvm-size -A` on the built ELF confirms `.cart_rom_bank_0` (13164 bytes, at `$8000`) and `.cart_rom_fixed_hi_extra` (13888 bytes, at `$C000`) are real, substantial, separate allocations -- not just individual symbols with plausible addresses. `llvm-nm` cross-checks every moved symbol lands where expected (`song_title`, `title_screen_data0/1`, `title_screen_zones`, `title_screen_loop` all in `$8000`-`$BFFF`; `misc_sprite_data`/`spaceship_data` at `$C000`+; `main`/`banked_call_8000` still in the fixed-lo `$4xxx` range). Header bytes and total size (128K + 128) match #24's SuperGame+POKEY@450 format exactly. Ran the real title->gameplay transition end to end via `test/atari7800/mame-lua/press_fire.lua` (the same scripted press/release-fire technique used since priority #20): a screenshot before firing shows the title banner/text rendering correctly *while running out of bank 0*; a screenshot after shows the ship/HUD/starfield/enemy rendering correctly in gameplay, having crossed the bank-switch boundary cleanly. A POKEY register trace across the same window shows continuous, changing register activity throughout (title theme, then a clean transition to level-1 music right after fire, matching #22's `atari7800_pokey_init()` re-silence-then-restart behavior) -- confirmed with real execution, not inferred. Full regression pass on the remaining flat `atari7800` examples (`palette-demo`, `displaylist-demo`, `asset-bridge-demo`, `pokey-min`, `title-demo`) shows no rebuild needed except `title-demo.a78` itself (its include-path update), which built and is otherwise unaffected.

## 27. Fix real fine-Y sprite corruption and a HUD-zone bullet-residual bug found via hands-on testing (Done 2026-09-12)

The user tested #26's build directly in the emulator (not just via scripted screenshots) and found two real rendering bugs neither the automated verification nor the earlier screenshots had caught.

Fixed the tool itself (not just papered over the one call site), rather than leaving a landmine for the next sprite that needs full shiftability.

Rather than give it its own array or a switchable bank (which, unlike the explosion, is drawn every single frame for every live enemy -- exactly the "must stay fixed, zero overhead" case the platform's own design principle calls out), folded it into the existing shared `misc_sprite_data` block as a third byte-column alongside star/bullet: all three need the identical 31-page envelope regardless of their own real content size, so extra columns in the same pages cost only a few dozen bytes instead of a whole new array -- the same "share one page block, different byte offset" technique already used repeatedly in this file, now proven to generalize to a real, independently-moving sprite too.
- **Bullets leaving stuck "residual" sprites when crossing the HUD row.** `update_bullets()`'s draw loop had no visibility clip at all, unlike stars (`if (star_y[i] >= 16)`, added specifically for this reason in an earlier session) and the enemy pool (#26 already clips `y < 16`, though for off-screen-visibility reasons, not this one). A bullet fired upward flies straight through `y < 16` -- the HUD's own zone, pinned static and never cleared per-frame -- and drawing into a static zone doesn't get reset like a normal one does, so the bullet's object header sticks there permanently. Added the same guard the star loop already uses.
- **Investigated but not a bug**: the user also asked about the HUD not matching the reference's real layout (two life "hearts," `E20` enemies-remaining, a bottom-left health bar vs. this port's placeholder "SHLD:100 L:3" text). Confirmed the glyph rendering itself isn't corrupted (`atari7800_build_glyph_run` cleanly skips/maps every character through a real `char_to_glyph` table, no garbage-glyph path) -- this is the already-known, already-listed "wire up the real HUD" gap (previous Next Steps entry), not a new rendering defect, and is unchanged by this pass.
- **Verification**: rebuilt and screenshotted repeatedly during active play (holding thrust to force continuous scrolling, firing in bursts) -- the corruption above fighters is gone across every frame checked, no bullet residuals accumulate near the HUD even under sustained firing through that row. Full regression pass: flat `atari7800` examples and `bank-min.a78` unaffected (the tool fix doesn't retroactively touch any other already-generated, already-committed asset header).

## 28. Fix enemy sprites truncating as they cross zone boundaries -- a real MARIA constraint, not a data bug (Done 2026-09-12)

Hands-on testing again (holding thrust to keep enemies scrolling continuously) found a second, distinct symptom past #27's fix: fighters intermittently lost their bottom half while moving, specifically while crossing a 16-line zone boundary.

- **Root cause: a single MARIA Direct Mode object's render window is exactly one 16-line zone.** Whichever zone an object is placed in (`y >> 4`), only that zone's own 16 scanlines are ever scanned from it, regardless of `draw_sprite_fine`'s shift -- there's no wraparound or cross-zone continuation at the hardware level. An 8-line sprite positioned such that `y & 15 > 8` needs more room than remains in its zone, and the overflow is simply never drawn (not corrupted data this time, a real, expected MARIA limitation). This is the exact same constraint `astrowing.bas`'s own `EnableObject`/`SetObjectY` macros are built around -- they only support two discrete positions (top-half/bottom-half) for an object shorter than a full zone, not arbitrary fine-Y -- and the same reason this file's own ship object stays permanently zone-aligned.
- **Investigated a true two-object split (render the overflow as a second object in the next zone) and found it doesn't close with the existing shared-array scheme.** Both objects would need the same shift value to read correctly, which (worked through in full) requires duplicating the sprite's content 16 pages further into the shared 31-page envelope -- but that same envelope is read by the *first* object's own window for the exact same crossing cases, since a 16-page window is too large relative to a 31-page total span to avoid the overlap. The result would be a second, different corruption: a ghost duplicate of the sprite appearing above the real one. A correct split needs a genuinely separate, non-shared data array per sprite -- real additional engineering, deferred rather than rushed.
- **Fix**: clamp the *drawn* Y (not the AI's own logical position, which stays fully smooth) so the sprite never straddles a zone line -- snapping to whichever safe position (bottom of the current zone or top of the next) is closer. `zone_safe_y_8`/`zone_safe_y_16` (astrowing.c, near `draw_sprite_fine`) handle the enemy sprite (9 of 16 possible offsets are safe) and the explosion animation (which, being a full 16 lines tall, only fits at shift 0 exactly -- always zone-aligned) respectively. Trades a small (<=4px) positional snap when crossing a zone for never showing a truncated sprite.
- **Verification**: 60 screenshots across ~900 frames of continuous forced scrolling (holding thrust) -- every fighter fully intact in every frame checked, no truncation at any point. Full regression pass: flat `atari7800` examples and `bank-min.a78` unaffected.
- Noted for later: the "true two-object split" this pass deferred would be worth revisiting once a level/boss system needs a taller or more precisely-positioned moving sprite than the 4px snap tolerance here allows.
